Does mKyber have ciphertext second
preimage resistance?
A proof note for a fixed recipient | 15 October 2026
Answer: yes for the explicit-rejection FO mKEM construction below, assuming the output hash
is collision resistant. This covers the FO architecture used for mKyber when instantiated with these
precise acceptance and output rules. A published theorem already establishes the stronger
collision-resistance result [1, Theorem 5].
The name "mKyber" alone is insufficient to identify every rejection and key-derivation choice. This note
keeps three profiles separate so that a theorem is not silently applied to a different algorithm.
Profile
Result proved here
Explicit rejection; accepted key H(m)
Recipient-local C2PRI follows from collision resistance of H.
Classical and quantum reductions preserve the attacker type.
Accepted key H(m); invalid key J(z,c)
Same accepted-path argument plus a fallback-preimage term. A
classical random-oracle bound is given.
Local key R(s,c) in both branches
C2PRI follows from collision resistance of R over injectively
encoded inputs. A classical random-oracle bound is also given.
What the result concerns
All claims concern one honestly generated recipient key and its actual, canonical ciphertext input c =
(u,v). They allow the attacker to know the full secret key. They do not assert uniqueness of the entire
multi-recipient vector, nor do they establish confidentiality, adaptive-corruption security, or security of
an MLS migration protocol.
Important correction to the earlier discussion
The relevant prior result is stronger than the tentative assessment previously given: Alwen et al.
explicitly analyze FO mKEM collision resistance [1]. The remaining task for the manuscript is to match
its chosen implementation to that construction, or provide the appropriate variant argument below. This
is an explanatory specialization and supplementary analysis, not a claim of a new cryptographic result.
Prepared using the supplied manuscript context and primary cryptographic sources. Definitions and algorithms are stated
explicitly; no implementation was supplied or certified.

1. Exact game and deterministic reconstruction
Fix the context
Fix public parameters pp and a recipient pair (pk,sk) generated by the scheme. All ciphertexts use one
canonical byte encoding. A ciphertext comparison must cover every input byte; parsing must reject
aliases or surplus bytes. The attacker may know pp, pk, sk and all public algorithm descriptions.
Let F_pk(m) be the deterministic reconstruction of a recipient ciphertext. In the decomposable FO
construction it uses the common coins G1(m) and recipient coins G2(pk,m), followed by the specified
encryption and compression. All context and parameters are fixed in this notation.
Encaps: sample m*; c* := F_pk(m*); K* := H(m*)
Decaps(sk,c):
m := PKE.Dec(sk,c)
if m is invalid or c != F_pk(m): return BOT
return H(m)
This is the explicit-rejection profile. G1 and G2 are deterministic for fixed inputs. The output hash H is
public. Encryption security is not an assumption of the argument below; its acceptance equality and
hash security are what matter.
Recipient-local C2PRI game
After the honest key generation and encapsulation above, give (pp,pk,sk,c*,K*) to attacker A. The
attacker outputs c'. It wins exactly when c' differs from c* and Decaps(sk,c') equals K*. This uses an
honest target and the same recipient key throughout. The secret key is deliberately exposed, as in the
X-Wing notion [2].
Do not replace this with another game
Allowing the attacker to choose two arbitrary ciphertexts is collision resistance, a stronger requirement
on the explicit-rejection construction. Allowing the recipient key to change, or comparing full vectors
whose unused entries are ignored, defines different questions. A same-key local theorem does not
silently cover those games.
Correctness and decryption errors
The direct proof on the next page uses the encapsulator's sampled m*, not a claim that decrypting c*
always recovers m*. Therefore its C2PRI bound needs no decryption-failure term. A black-box
conversion using only collision resistance of Decaps and correctness would ordinarily incur such a
term. This distinction avoids an unnecessary assumption in the direct argument.

2. Proof for the explicit-rejection profile
Theorem. For the stated profile, every C2PRI attacker A gives a hash-collision attacker B with
comparable running time such that
Adv_C2PRI(A) <= Adv_CR_H(B).
Proof. B generates the keys and target using m*. A successful c' passes re-encryption, so c' = F_pk(m')
and H(m') = H(m*). If m' = m*, determinism gives c' = c*, a contradiction. Thus (m',m*) is a collision in H.
B obtains m' using sk. Every success yields this collision. QED.
The related stronger collision-resistance theorem is already in [1, Section 5.3, Theorem 5; proof in
Appendix B.3]. The reduction above states the consequence directly for an honest C2PRI target.
Why secret-key exposure does not invalidate it
Knowing sk makes it easy to recover m* and to test ciphertexts. It does not create a second acceptable
ciphertext for that same message. The acceptance comparison still fixes F_pk(m*). The theorem
therefore does not rely on keeping m* secret or on hardness of recovering a lattice secret.
Classical and quantum scope
For the explicit-rejection profile, the reduction works with either attacker type, provided H has the
corresponding collision resistance. It is a reduction to a concrete hash property; it does not require
treating G1 or G2 as random oracles for this particular property. Other security claims about FO
encryption need their own assumptions.
What would invalidate this proof?
The argument does not apply unchanged if a receiver accepts without comparing the complete
canonical ciphertext, returns H(m) despite a failed check, allows fresh unrecorded encryption coins in
reconstruction, or ignores mutable bytes that are counted as part of c. These are deviations from the
stated profile. A wrapper may also introduce additional bytes outside this local KEM input; those need
separate authentication or binding.
Instantiating the result in the paper
To use this theorem, name the exact mKyber profile and confirm: reconstruction is deterministic;
equality is checked on canonical recipient ciphertext bytes; invalid deliveries return rejection; and the
accepted output is the specified collision-resistant hash of m. Select and state the output length and
hash assumption. "Uses FO" by itself does not provide this specification.

3. Implicit rejection with a common accepted key
This section is a separate extension, derived here. Replace only the failure branch by a
ciphertext-dependent fallback:
D(sk,c) = H(m) if c = F_pk(m), m = PKE.Dec(sk,c)
J(z,c) otherwise.
Here z is the recipient's rejection seed, included in the exposed secret key. H and J have disjoint
domains; J maps injectively encoded (z,c) to a lambda-bit string. Assume J is an independent random
oracle, and that key generation, m* selection, F_pk, and H do not use J. The attacker makes at most
q_J classical queries to J after receiving the target.
Theorem. Against classical attackers,
Adv_C2PRI(A) <= Adv_CR_H(B) + (q_J + 1)/2^lambda.
Proof by the branch taken on c'
Accepted branch. Let m' be the recovered message. Success requires H(m') = H(m*). If m' = m*,
deterministic reconstruction forces c' = c*, which is forbidden. Otherwise B outputs the hash collision.
The probability of success in this branch is at most Adv_CR_H(B).
Fallback branch. Success requires J(z,c') = K*. The target K* is fixed independently of J. Even though
z is known, each fresh classical J input has a uniform lambda-bit output and matches that fixed target
with probability 2^(-lambda). There are at most q_J queried inputs and one final input evaluated by the
game if A did not query it. A union bound gives (q_J+1)/2^lambda. Repeated queries add no fresh
chance. Summing the two branches proves the bound. QED.
Limits of this extension
Explicitly exposing z rules out an argument based only on PRF security with a hidden rejection key. The
assumption here is a public independent random oracle, so the claimed bound still applies when z is
public. The linear query bound is classical; it is not a proof for superposition queries. A QROM analysis
would require a separate quantum-search argument.
This extension preserves a common accepted output H(m) for all recipients. It is a precisely specified
variant; it should not be substituted for a cited implementation without checking that implementation's
success and rejection rules.

4. The ciphertext-dependent KDF rule in the overview
The cited NIST overview displays a local decapsulation rule that derives the output from both a pre-key
and the individual ciphertext, on success and failure [3]. Model that local rule exactly as
D(sk,c) = R(Encode(s(sk,c),c))
s(sk,c) = H(m) on acceptance
z on fallback.
Assume Encode is injective and includes the complete canonical c. For a matching recipient-local
encapsulation, the target is K* = R(Encode(s*,c*)). All other computations and the target R-input are
independent of R; this suffices for the random-oracle corollary below.
Theorem. If the public function R is collision resistant over its encoded inputs, then local C2PRI holds
with advantage at most Adv_CR_R(B).
Proof. Given a successful c', B computes x' = Encode(s(sk,c'),c') and x* = Encode(s*,c*). Since c' != c*
and Encode is injective, x' != x*. Success gives R(x') = R(x*). Thus B outputs a collision in R, regardless
of the acceptance/fallback branch. QED.
If R is an independent lambda-bit random oracle and A makes q_R classical queries, the same
fresh-query argument as on page 4 yields the sharper target-search bound (q_R+1)/2^lambda. Neither
argument needs lattice hardness or the FO check for this local property: the ciphertext is already an
input to R.
Do not silently equate this with a common-key mKEM
Distinct recipients generally have distinct c_i. Computing R(H(m),c_i) therefore generally yields distinct
output keys. The overview describes a common-key mKEM but also displays ciphertext-dependent
local outputs and an encapsulation symbol ct that needs clarification. This note treats the local rule
literally; it does not certify common-key agreement for an unresolved reading of that pseudocode.
For the manuscript, explicitly choose either the common accepted-key FO profile, or a fully defined
recipient-specific derived-key interface. The latter can be useful inside a transport wrapper, but it is a
different output interface from a conventional common-key mKEM. An arbitrary unspecified KDF is not
automatically a collision-resistant R.

5. Whole vectors and implications for your construction
A counterexample to a different, whole-vector property
Suppose C = (u,v_1,...,v_N), N >= 2, and recipient i only processes Ext_i(C) = (u,v_i). Choose j != i and
change v_j without changing the parsing or (u,v_i). Call the resulting vector C'. Then C' != C, but
D_i(Ext_i(C')) = D_i(Ext_i(C)).
Thus a naive property requiring recipient i to distinguish every change anywhere in the full vector is
false for this decomposable interface whenever honest decapsulation succeeds. This observation does
not contradict local C2PRI because Ext_i(C') = Ext_i(C): the actual local ciphertext has not changed. A
separate outer signature or global validation could reject a modified vector; that is an additional
mechanism.
What you can conclude now
Yes: the explicit-rejection FO construction has the recipient-local resistance in question, with the hash
assumption stated on page 3. Suitable implicit-rejection variants also admit the arguments above. No:
the decomposable interface does not supply the naive full-vector property just described.
This supports a more precise treatment of your combiner. Proving local C2PRI can help justify omitting
the PQ ciphertext from a suitable hybrid derivation. It does not by itself prove that your KDF, labels,
classical component, recipient selection, or MLS state transitions satisfy the applicable combiner or
group-security theorem. The adaptive-corruption issue for mKyber is a different security question.
