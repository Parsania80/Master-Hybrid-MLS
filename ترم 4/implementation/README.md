# Adaptive Hybrid MLS TreeKEM Research Prototype

## What is this?

This repository is intended to become a reproducible Rust research prototype for a thesis experiment. It will compare normal binary Messaging Layer Security (MLS), binary MLS augmented with experimental mKyber delivery, and an experimental adaptive transition from a binary tree to a quaternary tree.

## Why does it exist?

The experiment studies whether changing TreeKEM arity can reduce measured communication cost enough to justify a real transition cost, and when an old binary delivery cover can be retired safely according to the thesis formulas.

## What problem does it solve?

The planned software will create a valid 128-member baseline MLS group, replay controlled multi-member workloads, measure real serialized costs, evaluate transition start and end rules, verify member convergence, and generate reproducible CSV, JSON, and Markdown reports.

## Current status

The Rust workspace pins the approved dependencies and contains an unchanged OpenMLS 0.8.1 baseline adapter. It can create and join a standard group, stage and merge normal Add/remove/self-update commits from multiple members, process standard messages, and encrypt application data. Independent regression tests verify epoch, authenticated GroupContext, RFC tree-hash convergence, and application delivery. The Phase 2, Phase 4, Phase 5, Phase 6, Phase 7, and Phase 8 quality gates have passed on Rust 1.93.1. The Phase 8 gate ran locked-offline format, workspace check, strict Clippy, focused ArityState/TreeCover/transition-auth suites, baseline regression, all-target tests, doc tests, release build, metadata, OpenMLS feature audit, and diff validation. OpenMLS remains at 0.8.1 with only its RustCrypto feature. Bootstrap summaries archive only public provenance: the exact command, compiler, package, and direct dependency versions. The Phase 4 gate also runs bounded property tests for public mKyber wire mutations and verifies OpenMLS has only its RustCrypto feature enabled. The mKyber crate also implements `EducationalMkyber512Reference`, the paper-based `mkyber512-thesis-v1` profile: it validates the shared domain, emits exact 768/704/48-byte artifacts, and tests multi-recipient agreement, malformed input rejection, deterministic public-artifact reproducibility, and common/recipient tampering. A project-owned public regression digest is not an official KAT or interoperability vector. Normal reference calls use dedicated OS-RNG entry points; deterministic entropy is private to unit tests. Long-lived private keys and shared secrets are zeroized on drop, while temporary secret material uses scoped guards. It records component-only byte costs from actual serialized arrays: the 704-byte common component, each 48-byte recipient component, and their sum. The hybrid crate now performs complete isolated experimental path-level delivery: one mKyber encapsulation for the co-path recipient set, a context-bound 32-byte HPKE exporter secret and encapsulation per recipient, the canonical hybrid KDF input/expansion, and AES-128-GCM path-secret wrapping. Its instrumentation records actual public ciphertext lengths but zero KDF contribution. Tests reject every altered serialized delivery field, non-recipients, and group/epoch/tree-version/path-node replays without returning a path secret. The adaptive-tree crate now provides deterministic mapping plus immutable, public `Update`/`Add`/`Remove` replay. The metrics crate records a real emitted baseline Commit as `B_i(2)`, an explicitly labeled `shadow_exact_codec` candidate `B_hat_i(4)`, and typed public tree, recipient-resolution, crypto-count, and monotonic timing facts. The transition-policy crate retains an accepted-commit trail, exact preflight savings, a five-condition start evaluator that records every public blocker, and byte-or-fixed-point-percent Delta resolution. It schedules nothing and does not construct or accept a transition Commit. This is thesis-local educational reference code, not an author-approved profile or vector corpus; it makes no interoperability, audit, side-channel, security-proof, business, or production claim. `SECURITY.md` records the non-standard protocol changes, threat model, interoperability boundary, X-Wing/C2PRI limitation, and unresolved assumptions. See `PROJECT.md`, `SECURITY.md`, `docs/adr/`, and `SESSION-LOG.md` for the authoritative decisions and audit trail.

Transition-start Delta is now configurable as either absolute bytes or a fixed-point micro-percent of the current transition preflight. A percentage resolves with checked integer arithmetic and ceiling byte rounding; the typed future-CLI override has explicit precedence over TOML. There is still no transition-evaluation CLI or live transition Commit.

The prototype now also validates a canonical public `ArityState` extension value for the first `2 -> 4` transition. It records policy thresholds, evaluation facts, tree version, and mapping/TreeCover hashes, but it is not yet placed in or authenticated by an MLS GroupContext extension; that fork integration remains future work.

The active quaternary topology and old binary TreeCover are now distinct public structures. Only the quaternary side is marked as the future epoch-secret authority; the TreeCover is delivery-only, excludes post-transition additions, and revokes a frozen member on removal. Neither structure derives secrets or changes a live MLS group.

Transition metadata now has a fail-closed pre-apply validator. It checks the exact private-use state extension, mapping/TreeCover bindings, and group/epoch/tree-version/arity/GroupContext-hash agreement with the hybrid context before returning public transition state. A future experimental fork must still provide the already MLS-authenticated GroupContext facts and apply them atomically.

Task 44 adds an educational in-process batch harness around that boundary. It first validates every member's metadata and opens every recipient-specific hybrid path secret, then replaces public member snapshots only if all stages succeeded. Tests show three recipients converge for independent Alice and Bob committer scenarios, while divergent metadata, a later recipient-resolution failure, or a tampered hybrid ciphertext leaves every harness member unchanged. This is not live MLS Commit processing, distributed/network atomicity, or a security/interoperability claim.

Task 46 measures the four TreeCover-maturity inputs for each public recipient set: independent leaf delivery, current new-tree delivery, eligible old-TreeCover delivery, and ideal mature-quaternary delivery. Every available value is the exact sum of canonical hybrid TLS ciphertext bytes for routes that cover the set exactly once. Empty or unavailable routes keep a typed reason instead of a made-up zero. These are serializer-driven counterfactual component costs, not measured network traffic or full MLS Commit sizes.

Task 47 turns those inputs into exact rational maturity facts. It keeps both raw and `[0, 1]`-clamped values, records whether clamping occurred, uses the lowest new-tree score and highest old-TreeCover score across non-empty target sets, and retains undefined inputs as blockers. It does not decide retirement yet.

Task 48 applies the thesis retirement rule exactly: retire only when new-tree maturity is at least 0.70 or old-TreeCover maturity is strictly below 0.50. It uses fixed-point integers, records which side triggered, and blocks any undefined non-empty target set. It does not retire or erase anything yet.

Task 49 adds the educational retirement boundary. A future experimental MLS fork must supply the Task 48 `Retire` decision and facts from the same already authenticated GroupContext/Commit transaction. The harness accepts only a canonical normal quaternary state at the next epoch and tree version, records the trigger and public commitments, and stages all member snapshots before replacing any of them. It has no real TreeCover secret store: it explicitly records that no secret material exists here, rather than claiming that an MLS secret was erased. It is not live MLS Commit processing, distributed atomicity, an interoperability feature, or a security proof.

## How to use it

The 128-member baseline constructor is available now: `cargo +stable run --bin bootstrap_128 --release --locked --offline -- --members 128 --seed 42 --output output/bootstrap-128`. The public seed selects committers only; it is not cryptographic entropy. After verification, the command writes create-new public artifacts under the requested `output/<run>` directory: `bootstrap_public_snapshot.json`, `bootstrap_128_summary.json`, `bootstrap_128_commits.csv`, and `bootstrap_128_report.md`. The snapshot contains public configuration/scheduling data, authenticated group metadata, the public TLS RatchetTree, occupied leaves, and the 127 actual Add KeyPackages. The CSV contains only public per-commit identity, epoch, byte-count, and delivery-count observations—not Commit bodies or ciphertexts. None of these files contain private MLS state, secret material, raw entropy, or a seed that reconstructs it.

Before the constructor reports success, it verifies 128 members at epoch 127, baseline binary arity 2 and height 7, actual occupied public leaf indexes `0..127`, common authenticated GroupContext/tree hash, and application delivery to every other member. It returns public facts only and then drops private client state; that lifecycle action is not a formal proof of upstream process-memory zeroization.

Run `cargo +stable test --workspace --all-targets --locked --offline` to verify the baseline and educational mKyber reference tests. Run `cargo +stable run -p mkyber --bin mkyber_benchmark --release --locked --offline` for the standalone reference timing smoke benchmark. It prints only the reference profile/parameters, actual public 704/48-byte component costs, and environment-dependent timing averages; it is not a production benchmark, security evaluation, or thesis experiment result. Generate a baseline report and plots with `cargo +stable run -p report --bin generate_baseline_report --release --locked --offline -- --group-id <PUBLIC_ID> --initial-members <N> --maximum-members <N> --operations <N> --regions <N> --workload mixed --committer round-robin --output output/<run> --report report/<run>`.

Generate the current availability-aware three-mode comparison with `cargo +stable run -p report --bin compare_modes --release --locked --offline -- --baseline-config configs/task57-baseline.toml --mkyber-config configs/task57-mkyber.toml --adaptive-config configs/task57-adaptive.toml --initial-members 2 --maximum-members 4 --operations 6 --regions 2 --output output/<run> --report report/<run>`. It creates `mode_comparison.csv`, `mode_comparison.json`, and `mode_comparison.md`; only baseline is executed today.

## Security and interoperability warning

This is educational thesis research software, not production cryptography, and it is not recommended for business or production use. All mKyber, hybrid path-secret, adaptive-tree, and TreeCover behavior is non-standard and experimental. Experimental modes must not claim RFC 9420 interoperability or a formal security proof.

The thesis specifically requires the post-quantum ciphertext to be transmitted and authenticated while excluding it from the hybrid KDF input. That omission is an experimental design choice and is not automatically covered by the X-Wing C2PRI security argument. Reports must never contain shared secrets, path secrets, private keys, AEAD keys, raw entropy, or seed material that reconstructs private state.
